# Release Notes: v0.1.0

**Release Date:** 2026-09-08

## Highlights

Initial release of systemspec-crypto: a Go-first, machine-readable
intermediate representation for describing the cryptography a system uses —
what crypto exists, where and why it is used, how it is configured, and what
evidence supports those claims. The IR holds **facts and evidence, never prose
answers**; questionnaire responses, posture findings, and CycloneDX CBOM
documents are projections over it.

Two invariants shape the model and make it safe to build on:

- **Capabilities are not usage.** An implementation records what it *can* do
  (`capabilities`) separately from what the system actually *does* with it
  (`usedCapabilities`), so a scanner or language model can never turn "the
  library supports X" into "the product uses X".
- **Facts carry verification.** Every claim records a verification state
  (`discovered → inferred → review-required → verified → attested`), so an
  AI-inferred fact and a human-attested one stay distinguishable.

Dogfooded end to end on the public `plexusone/omniagent` platform and exported
to a CycloneDX 1.6 CBOM.

## What's New

### Core IR

`cryptospec.Spec` is the canonical document: `Implementation`, `Algorithm`,
`Use`, `Claim`, `Evidence`, plus the shared `Lifecycle`, `Provenance`, and
`Verification` primitives. See the [Specification](../spec.md) for the full
normative model.

```go
import "github.com/plexusone/systemspec-crypto/cryptospec"

spec := cryptospec.Spec{
    SpecVersion: cryptospec.SpecVersion,
    System:      cryptospec.SystemRef{ID: "example-service", Name: "Example Service"},
    Implementations: []cryptospec.Implementation{{
        ID:               "impl:go-stdlib",
        Type:             cryptospec.ImplementationLibrary,
        Name:             "Go standard crypto",
        Capabilities:     []string{"SHA-256", "AES-256-GCM"},
        UsedCapabilities: []string{"SHA-256"},
    }},
    Algorithms: []cryptospec.Algorithm{{
        ID: "algorithm:sha-256", Name: "SHA-256", Class: cryptospec.ClassHash,
    }},
    Uses: []cryptospec.Use{{
        ID: "use:artifact-integrity", Purpose: cryptospec.PurposeIntegrity,
        AlgorithmRef: "algorithm:sha-256", ImplementationRef: "impl:go-stdlib",
    }},
}
```

### The `Use` object

A cryptographic inventory can say SHA-256 exists; a `Use` says SHA-256 is used
for artifact integrity, in a given component, with a given configuration
(salt/iterations/parameters), at given source locations, backed by given
evidence. One `Use` answers many differently-worded questions.

### Validation

`validate.Validate` checks referential integrity, `usedCapabilities ⊆
capabilities` (when capabilities are enumerated), controlled-vocabulary
conformance, type-prefixed ID conventions and uniqueness, and the requirement
that verified/attested claims carry evidence. Cryptographic *posture* (weak
algorithms, outdated libraries) is deliberately out of scope — that is a later,
policy-driven linter whose findings are ephemeral and kept out of the spec.

### CLI

```bash
go install github.com/plexusone/systemspec-crypto/cmd/cryptospec@v0.1.0

cryptospec validate crypto.json                 # structural rules; non-zero exit on errors
cryptospec report   crypto.json                 # human-readable internal summary
cryptospec cbom export crypto.json -o crypto.cbom.json   # CycloneDX 1.6 CBOM
```

The same commands mount under a family aggregate CLI as `systemspec crypto …`
via `cli.NewCommand()`; all capability lives in importable packages, with
`cmd/cryptospec` a thin adapter.

### Go-first schema

Go structs are the source of truth. `schema/crypto.schema.json` is generated
from them and passes `schemakit lint --property-case camelCase` with zero
findings, guaranteeing the model maps cleanly to statically-typed languages.

### CycloneDX CBOM export

`cryptospec cbom export` projects a spec into a CycloneDX 1.6 CBOM — the system
as an application, implementations as libraries, algorithms as
cryptographic-asset components. Because CBOM cannot carry usage purpose,
configuration, evidence, or verification state, the export is a lossy
projection and reports what it drops rather than losing it silently.

## Dogfood

`examples/dogfood/omniagent.json` describes the cryptography of the public
`plexusone/omniagent` platform, discovered by source analysis: Argon2id
password hashing, SHA-256 token hashing, ECDSA/RSA JWT signature verification,
`crypto/rand` CSPRNG, and gorilla cookie authentication. Every fact carries an
evidence locator and a verification state; the library-default session cookie
MAC is honestly recorded as `inferred` rather than `verified`.

## Conformance

- A shared fixture corpus under `examples/fixtures/{valid,invalid}` is exercised
  by both the Go validator and JSON Schema validation; valid fixtures also
  round-trip Go → JSON → schema without loss.
- `go test ./...`, `golangci-lint`, and `schemakit lint` all run clean in CI.

## Known limitations

Key management, certificates, protocols, and data-protection detail; CBOM
import; the posture linter; and crypto-agility / PQC / RAS / disclosure models
are planned for later revisions — see the
[ROADMAP](../specs/initiatives/INIT-SYSTEMSPECCRYPTO-001/ROADMAP.md). The spec
never stores secret material; that is a permanent invariant.
